# 模块 04：需求功能点拆解与确认

状态：已实现，待用户验收。本轮不生成测试用例。

## 使用流程

项目 → 需求列表 → 某份需求的“功能点” → AI 拆解 → 核对和编辑 → 保存功能点 → 勾选范围并保存 → 确认测试范围。

AI 使用模块 03 已保存的模型配置，真实模式下会把本份需求的标题和正文发送给模型。Mock 必须由用户在设置页显式开启，结果标记为“Mock 示例（未联网）”，只用于验证操作流程。

生成结果先在浏览器预览，不自动写库。新增、移除、编辑和范围选择也先作用于页面，点击“保存功能点”后一起写入数据库。编辑弹窗的“应用到清单”只更新当前页面，不等于保存。

## 范围和数据

功能点字段：模块、名称、功能描述、验收标准、约束/待澄清、优先级（P0/P1/P2）、是否纳入范围。每份需求最多 50 个功能点。

新增两张表：

- `feature_sheets`：以需求 ID 为主键，保存清单版本、对应需求原文的哈希、来源、模型标识和确认状态。
- `features`：每个功能点有稳定 UUID，关联清单，保存上述字段和排序。

人工编辑和保存保持已有功能点 ID，新增产生新 ID；重新 AI 拆解产生一份新预览，因此分配新 ID。当前阶段尚无用例引用，后续用例生成将使用功能点 ID 和输入快照建立关联。

删除需求或项目会级联删除功能点和清单。当前只新增表，后端重启时可自动建表，不修改已有表结构，也不读取或替换用户的模型配置。

## 预览、保存与确认

| 状态 | 含义 |
|---|---|
| 未保存 | 页面有新预览、人工编辑或范围选择，尚未写库 |
| 待确认 | 已保存，尚未确认测试范围 |
| 已确认 | 清单已保存，至少选择了一项，用户确认范围 |
| 需求已变化 | 标题或正文与上次保存清单时不同，原确认失效 |

编辑后再次保存会回到待确认。需求原文变化时，旧功能点保留以便比较，但后端返回的有效确认状态为 false。用户可重新 AI 拆解，也可核对旧清单并保存，然后再次确认。

清单保存使用 `expected_revision` 防止其他页面的新版本被覆盖；需求内容哈希防止旧原文生成的预览写到已更新的需求上。冲突返回 409，页面保留当前输入；需核对或复制需要保留的修改，再重新加载，当前不做自动合并。

保存时先对对应需求做条件写入取得 SQLite 写锁，再检查清单版本并在同一事务内更新清单和功能点。这样同时保存不会跳过版本检查。模型调用前释放数据库事务，网络等待期间不持有写锁。

## AI 解析与限制

`prompts/feature_parser.md` 约束模型只返回 `{"features": [...]}`，不虚构需求中的阈值、错误码和业务规则。结构校验检查必填字段、类型、长度、优先级和 1–50 项数量；接受纯 JSON 或完整 JSON 代码块，不从任意解释文字里猜测提取。

结构校验不保证业务正确性，仍需人工核对。无效 JSON、空列表、缺字段、无效优先级、响应截断或网络错误均提示失败，不覆盖已有功能点，也不切换 Mock。

本模块为同步解析，最多等待模型配置中的超时时间，输出上限 4096 Token。模型输出达到长度上限时提示拆小需求；本阶段不做后台任务、暂停和断点续跑。未保存预览在离开/刷新后可能丢失，页面会提示。

针对 DeepSeek 官方域名，本阶段的连接测试和功能点拆解均显式关闭思考模式，以便稳定获得文本 JSON。这是当前模块的策略，不修改用户保存的模型名称、Key 或超时。

## 接口与代码导读

统一前缀：`/api/projects/{project_id}/requirements/{requirement_id}/features`。

| 方法 | 后缀 | 作用 |
|---|---|---|
| GET | 无 | 获取已保存清单、当前原文哈希和有效确认状态 |
| POST | `/analyze` | 读取已保存需求和模型配置，生成预览，不写库 |
| PUT | 无 | 原子保存清单；`confirmed=true` 时同时确认范围 |

跨项目或不存在的需求返回 404；非法输入返回 422；原文或版本冲突返回 409；模型响应错误返回 502，超时返回 504。

推荐阅读顺序：

1. `backend/app/models.py`：`FeatureSheet` 和 `Feature` 的外键关系。
2. `backend/app/schemas.py`：功能点字段、输入校验与预览/清单响应。
3. `backend/app/prompts/feature_parser.md`：输出协议和事实约束。
4. `backend/app/llm.py`：从连接探针提取出的共用 `chat_completion()`。
5. `backend/app/features.py`：预览解析、内容哈希、版本检查和保存事务。
6. `web/src/pages/RequirementFeatures.vue`：页面预览、弹窗草稿、dirty 状态、保存和确认。
7. `backend/tests/test_features.py`：如何验证失败不覆盖、跨项目隔离、原文失效和版本冲突。

实际调用仍通过已有轻量 HTTPX 适配器；更复杂的 LangChain/LangGraph 编排在后续模块加入，不在这一模块引入工作流运行时。

## 手工验收

- [ ] 在需求列表点击“功能点”，能进入对应需求的页面并查看原文。
- [ ] 点击 AI 拆解后显示结果和来源；真实模式使用你的模型，Mock 结果有明确标记。
- [ ] 生成后显示未保存；刷新/离开时提醒，尚未保存的预览不会悄悄入库。
- [ ] 编辑模块、名称、描述、验收标准、约束和优先级，应用到清单后保存，再刷新，结果保留。
- [ ] 新增功能点，必填项不能为空；取消编辑可保留或放弃未应用修改。
- [ ] 移除功能点先取消，清单不变；确认移除再保存，数据库中才删除。
- [ ] 取消部分功能点的“纳入范围”，保存后选中数量与刷新结果一致。
- [ ] 未保存、没有选中项或需求已变化时，不能确认；保存有效选择后可确认。
- [ ] 已确认清单编辑并保存后回到待确认。
- [ ] 修改需求原文后返回，提示需求已变化且不再有效确认；核对保存后可重新确认。
- [ ] 两个页面读取同一版本，先后保存，后保存者收到冲突提示，输入保留，不覆盖先保存的数据。
- [ ] 再次拆解时先提示替换当前预览；取消不改变清单；模型失败也不改变原有内容。
- [ ] 不同项目的需求和功能点互不串用；删除测试需求后其功能点一并删除。
